# Multi-Tenant Business Migration Design

## Goal

Extend the independent login demo into a standalone multi-tenant version of the Smart Trade business application. Authenticated users receive isolated company workspaces and can use the migrated business modules. The existing trial, license, and activation controls remain intact; this design does not remove or bypass them.

## Scope

The migration covers the original application's business areas in staged slices:

1. Identity and workspace context.
2. Company and customer management.
3. AI chat, conversation history, memory, and skill routing.
4. Orders, quotations, document libraries, templates, and technical drawings.
5. Scheduled jobs, OSINT, email, LinkedIn, and related external capabilities.
6. The complete authenticated workbench UI.

The first release uses one default workspace per account. Workspace membership, invitations, teams, billing, and external identity providers are deferred until the core migration is stable.

## Tenant model

- `users` stores login identity and password hash.
- `workspaces` stores a company space owned by a user.
- Migrated business tables receive a non-null `workspace_id` foreign key.
- The authenticated session contains only `user_id`; the server resolves the user's workspace and never trusts a client-provided user or workspace ID.
- Every read, update, delete, and business action is scoped to the resolved workspace. Missing or mismatched scope returns a safe not-found/forbidden response without leaking another workspace's data.
- Existing local data is not exposed automatically. Import/migration must explicitly assign it to a workspace.
- Workspace-specific files live below a controlled workspace directory; paths are generated by the server and never accepted as arbitrary filesystem paths from the browser.

## Application architecture

The `login-demo/` application becomes the new authenticated shell. Its FastAPI app owns login, session handling, workspace resolution, static assets, and migrated API routes. Business logic is ported in focused modules rather than imported wholesale from the original `trade` package, so the new app has an explicit tenant boundary. The migration may temporarily use adapters around original logic, but adapters must receive a resolved workspace context and must not expose unscoped database access.

The browser always uses same-origin APIs. Unauthenticated requests are limited to the login/register page and auth endpoints. Authenticated requests receive a workspace context from the server. External providers and scheduled workers must receive an explicit workspace identifier and load that workspace's credentials/configuration.

## Migration stages

### Stage 1: Identity and workspace context

Add workspace creation at registration, session-to-workspace resolution, request dependencies, database migration helpers, and isolation tests. No business feature is enabled until this boundary is enforced.

### Stage 2: Company and customer data

Port company, customer, contact, and basic settings CRUD. Add workspace filters to all repository functions and verify two accounts cannot read or mutate each other's rows.

### Stage 3: Core workbench

Port chat streaming, conversation history, memory, prompt/skill routing, and agent context. Conversation and memory records must carry workspace scope; streaming errors must not reveal another workspace's data.

### Stage 4: Business operations

Port orders, quotations, libraries, templates, document tasks, and technical drawings. File storage and database rows share the same workspace ownership checks.

### Stage 5: Automation and external capabilities

Port cron bindings, OSINT, email intelligence, LinkedIn-related workflows, and external API configuration. Background jobs carry workspace context explicitly and cannot use a process-global current user.

### Stage 6: UI parity

Bring over the original workbench navigation and panels behind the authenticated shell. Replace original client-side company selection assumptions with the server-resolved workspace. Keep the login/register view separate from the business shell.

## Error handling and security

- Invalid login remains a generic 401 response.
- Invalid input returns validation errors without stack traces.
- Cross-workspace resource access behaves as not found or forbidden without disclosing whether another workspace's record exists.
- Passwords remain salted PBKDF2 hashes; sessions remain signed, HttpOnly, SameSite=Lax cookies.
- No API accepts `user_id` or `workspace_id` as an authority source from the browser.
- File uploads/downloads validate ownership before filesystem access.
- Trial, license, and activation decisions remain in their existing authorized logic.

## Verification strategy

Each stage adds unit and API tests before implementation. Required regression coverage includes:

- Registration creates exactly one default workspace.
- Two accounts can use the same business feature without seeing each other's rows or files.
- A forged or mismatched workspace identifier cannot change authorization.
- Authenticated and unauthenticated UI states render correctly.
- Existing license/trial tests remain unchanged and passing in the migrated service.
- The standalone app has no unscoped imports or direct access paths that bypass tenant context.

## Acceptance criteria

- A user can register, log in, and enter a default company workspace.
- All migrated business data is owned by a workspace and filtered by the authenticated workspace context.
- The original business areas are migrated in the six stages above with tests at each boundary.
- The new app remains independently runnable and does not rely on the login user bypassing original licensing controls.
